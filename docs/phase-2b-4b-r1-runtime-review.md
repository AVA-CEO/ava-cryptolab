# R1: machine preflight and offline calculator security review

Assessment date: 2026-10-23. **R1 only. No installation or runtime activation is authorized.** Findings are snapshots, not a performance benchmark or a guarantee of future availability. Proposed policies and R2 steps below require owner sign-off.

**Decision:** the CPU, Windows edition and installed RAM make this laptop a plausible Docker Desktop/WSL 2 host, but it is **NOT READY to start an additional calculation VM under the observed workload**. Available RAM was only 2.28–2.73 GiB; WSL prerequisites are disabled; storage has limited margin. Prefer Docker Desktop with WSL 2 conditionally, after the resource and approval gates below. Do not install merely because total RAM is 16 GiB.

## 1. Method, privacy and boundaries

Used narrowly projected read-only CIM queries, selected service states, current-profile package/uninstall metadata, binary file-version metadata, current-profile WSL registration metadata and aggregate memory for selected generic process names. No serial numbers, licence keys, device names, account identifiers, process command lines, window titles or personal file contents are included. Paths in future commands use placeholders or environment variables, not personal profile paths.

The initial sandboxed CIM queries were denied. A separately approved read outside the workspace sandbox succeeded. This permission allowed metadata access; no command requested UAC elevation, changed Windows settings or started/stopped a service. Optional features were inspected through CIM, not administrative DISM servicing.

No `wsl`, `wslc`, Docker, Podman or VM-management executable was invoked. In particular, the WSL stub was not executed to obtain a version or list: the relevant services/package were not detected and the features were disabled, so invoking it was unnecessary risk under the no-launch restriction. No distribution, VM, game or runtime was started. No installers, images or software artifacts were downloaded; official documentation was read online.

No normal journal, preserved backup or existing practice database was opened, hashed or modified. No application source, migration, dependency, security setting or `.vscode/` content changed. Only this document and the learning journal are edited. No commit or push is included.

## 5. Proposed approved-release security contract

This is a policy proposal for sign-off, not an activated release or an assertion that a signing dependency is installed. It preserves B1's versioned, offline OCI execution requirement and does not amend accounting.

### Immutable package and financial contract

Use a platform-specific **linux/amd64** calculator image for this x64 CPU, without implicit emulation. The build allowlist contains the existing CFD calculator, required schemas, a minimal adapter and pinned dependencies. No broker SDK, application database, uploads, credentials, `.env`, Git authentication material or normal journal belongs in it. Do not change crypto or CFD formulas while packaging.

Pin the base-image manifest and final platform image-manifest SHA-256, image configuration digest, exact CPython patch/build, dependency versions and wheel hashes, source commit/tree hashes, build recipe, contract/serializer/verifier versions and platform/ABI. Preserve wheel files for offline rebuilding. Rebuilding is not automatically bit-identical; retaining the original approved image is the replay source.

Source review confirms the current CFD context: precision **160**, arithmetic `ROUND_HALF_EVEN`, Emin **-999999**, Emax **999999**, traps for InvalidOperation, DivisionByZero and Overflow. Record these plus caller-supplied presentation rounding, currency precision, recognition `incurred_once`, fixed original-risk basis and dated FX policy. Raw and displayed Decimal amounts remain strings. An upgrade must not change old inputs, risk, results or policy labels.

OCI digests identify specific content; an image manifest, configuration digest, source hash and archive checksum are not interchangeable. The approved B1 mapping is retained: `engine_build_sha256` stores the 64-hex component of the platform image-manifest digest, while the full `sha256:...` reference stays in the signed manifest. [OCI descriptors](https://github.com/opencontainers/image-spec/blob/main/descriptor.md). The accepted input/result canonicalizer remains a separately reviewed version; never relabel B2's test serializer or B3B-R's `synthetic-read-json-v1` as an accepted version.

### Signed manifest and approval registry

Proposed identity: `ava-cfd-release-envelope-v1`, with payload schema `ava-cfd-release-v1`. Payload includes the release ID, all package hashes/versions above, engine ID, supported modes/currencies/contracts, Decimal rules, resource profile, golden-test-set digest and creation time. Financial observations are not part of the software-release manifest.

Proposed algorithm: **Ed25519**, SHA-256 for content digests. The owner must approve this choice before implementation. Do not silently negotiate another algorithm. Proposed signature input is the ASCII prefix `AVA-CFD-RELEASE-V1` followed by LF, then RFC 8785 canonical UTF-8 payload bytes. No signature or self-hash field is included in that payload. Reject duplicate keys and ambiguous numeric encodings; financial settings use strings and bounded integer limits.

The envelope contains payload, algorithm, public-key ID and base64 signature. Key ID is SHA-256 of the public key's SPKI DER representation. Store `manifest_sha256` over the complete canonical envelope, including signature metadata, but excluding any self-hash field. The image archive is separate from its signed manifest, avoiding circular archive/manifest hashes. Pin serializer/signature encodings and test vectors before freezing this profile.

Ed25519 is supported by Sigstore's self-managed-key ecosystem; a pinned reviewed local verifier must be selected and independently qualified. Cosign bundles are an alternative transport/profile, not assumed byte-compatible with this proposed detached envelope. Selecting a bundle instead requires an explicit profile update and tests. No key generation, new crypto dependency or tool installation happens in R1. [Key support](https://docs.sigstore.dev/cosign/key_management/signing_with_self-managed_keys/), [local verification](https://docs.sigstore.dev/cosign/verifying/verify/).

Execution requires both a valid signature from an owner-pinned key **and** an owner-approved release/digest registry entry. A valid publisher signature is not automatic approval. Do not trust a key merely because it arrived beside an image or appeared in a request. Clients cannot supply executable paths, registry tags, URLs, manifests or trust keys.

### Key lifecycle and offline verification

- Generate any future private signing key in a separately approved signing environment, encrypted with access limited to the release maintainer. Keep it outside the executor, repository, image, journal machine settings and ordinary logs. Keep its recovery copy separately protected; no production key is created now.
- Executor receives only approved public keys and a versioned approval registry. Pin key IDs and verifier version; key/registry changes require explicit owner review. Keep historical public keys and trust decisions for verification.
- Rotation adds an approved new key and reviewed activation date; retired keys cannot authorize new releases. Do not silently re-sign or rewrite historical trading evidence. Revocation blocks affected new execution; preserve past evidence with explicit trust/replay status. A valid signature proves publisher identity, not broker authenticity or mathematical correctness.
- Verify local archive checksum, signed manifest, allowlisted platform image/configuration digests, policies and resource profile before loading/executing. Never equate a Docker image ID with the OCI manifest digest. Missing trust, artifact or runtime means unavailable; no automatic pull, remote key discovery or host-Python fallback.
- Use an offline trust store. No live OIDC, transparency-log, KMS or certificate fetch may be an execution dependency. If a future scheme requires signed-time/log evidence, archive it and qualify the offline verifier rather than disabling checks to make it work. Offline revocation freshness depends on deliberate signed trust updates; disclose this limit.

### Sandbox and historical recovery

The container receives one bounded JSON request over stdin and emits typed JSON over stdout. Use structured process arguments, not shell-built commands or large request data in Windows command lines. Deny network, port publishing, privileged mode, added capabilities, Docker sockets, devices, GPU, host namespaces and arbitrary mounts. Run non-root, read-only root filesystem, no-new-privileges, default seccomp plus reviewed restrictions, and only a bounded private tmpfs if needed. Scrub inherited environment and fix locale/timezone; user-supplied source labels never become paths or commands. [Runtime controls](https://docs.docker.com/reference/cli/docker/container/run/).

Deadline handling must stop the owned container/process tree, not only cancel the HTTP waiter. Output, memory and PID limits must be enforced while running. Reject unsupported runtime flags or unenforced limits rather than treating them as best effort. Runtime startup/install/update is never triggered by GET, normal application startup or a preview request. A separate approved readiness action brings it online.

For each accepted release retain its original OCI blobs/manifests, signed release envelope, exact dependency/wheel archive, source/build recipe, verifier/canonicalizer, public trust history, runtime/platform requirements and golden fixtures. Keep two checksum-verified copies in separately approved private locations outside Git. Image export formats require actual load/digest qualification; filesystem export is not a replacement for the original image. [Docker archives](https://docs.docker.com/reference/cli/docker/image/save/), [Podman formats](https://docs.podman.io/en/stable/markdown/podman-save.1.html).

Never garbage-collect a release referenced by retained records without owner-approved retention/recovery policy. Rehearse restoration into a fresh isolated image store with registry access blocked; verify signatures/digests and reproduce canonical golden outputs. If the old platform or verifier cannot run, return replay unavailable and retain readable evidence under its verification policy. Do not substitute today's release. Key backup alone is not image backup; image backup alone is not proof of replay.

### Separation from today's synthetic fixtures

Existing B2 test manifests and B3B-R's exact synthetic manifest remain **synthetic**, without an approved signature/release. Future `approved_release` requires verified signature, pinned artifact and owner approval; it never means broker-authentic data. Current read verification supports only synthetic manifests. Accepted-evidence verifier support must be separately reviewed before accepted saving. The preview route deliberately returns 503 even if an accidentally returning provider is inserted; installation alone cannot enable it. No fixture is promoted and no existing evidence is rewritten.

## 6. R2 installation proposal — DO NOT EXECUTE IN R1

R2 should be split into **R2A artifact/feature/install approval** and **R2B first-start/configuration qualification**. Downloads, administrator actions, reboots, first launches and configuration must be explicitly covered; neither gate enables financial calculation or container workloads.

### R2A: exact ordered preparation and installation

1. **Approval required:** accept the preferred Docker/WSL route, proposed security policy and resource gates. Recheck current free RAM/disk without launching anything. Stop if headroom is insufficient. Obtain the owner's dormant-VM/VPN/gaming impact review; do not stop any application or change VBS.
2. **Approval required:** choose the private staging/archive locations and final storage budget. Do not scan, move or delete existing personal files/backups to make room. With the current measurements, a 20 GiB reserve leaves only 11.53 GiB for all new runtime and temporary artifacts.
3. **Download approval required:** obtain only owner-approved x64 stable installers from [Microsoft WSL releases](https://github.com/microsoft/WSL/releases) and [Docker release notes/checksums](https://docs.docker.com/desktop/release-notes/). Current research candidates are **WSL 3.0.3** and **Docker Desktop 4.96.3**; revalidate security notes before a final pin. Never silently resolve `latest` during installation. No bytes or checksums were downloaded or fabricated in R1.
4. **Inspection approval required:** record the exact asset filename/size/version, official SHA-256 and verified publisher/signature before execution. For downloaded approved files, compare `Get-FileHash -Algorithm SHA256` with the official checksum and inspect `Get-AuthenticodeSignature`; require Valid and the expected Microsoft/Docker publisher. If the official independent checksum/signature or download identity cannot be established, stop. A hash calculated only from the downloaded file is not independent verification.
5. **Administrator feature-change approval required:** enable only the two currently disabled WSL prerequisites with the following planned commands. Full Hyper-V, HypervisorPlatform, BIOS settings and existing security configuration are not part of this proposal.

```powershell
# PLAN ONLY — needs separate R2A approval and an owner-approved admin session.
dism.exe /online /enable-feature /featurename:Microsoft-Windows-Subsystem-Linux /all /norestart
dism.exe /online /enable-feature /featurename:VirtualMachinePlatform /all /norestart
```

6. **Restart approval required:** stop for the owner to save work and schedule the requested reboot. Never force a restart or terminate the journal/VS Code/game processes automatically. Reinspect feature states afterward; pending restart is not success.
7. **Installer/UAC approval required:** install the pinned, verified WSL x64 MSI using its interactive installer. A planned invocation is `msiexec.exe /i "<approved-wsl-x64.msi>" /norestart`; the actual absolute file path must be reviewed first. Do not add Ubuntu or import any existing distribution. Confirm the WSL product version afterward; the Windows `wsl.exe` file version is insufficient. Any additional reboot requires another owner decision. [Microsoft prerequisites](https://learn.microsoft.com/en-us/windows/wsl/install-manual), [official WSL release](https://github.com/microsoft/WSL/releases/tag/3.0.3).
8. **Installer/licence approval required:** open only the verified Docker installer, choose **per-user / WSL 2 / Linux containers**, and let the owner review the terms. Planned installer options are `install --user --backend=wsl-2`, not unattended licence acceptance. Do not add `docker-users`, install an all-users service, select Docker VMM Beta, enable Kubernetes or modify development interpreters. Stop before first launch. [Installation modes](https://docs.docker.com/desktop/setup/install/windows-install/).

These steps are a proposal, not a ready-to-run script: final asset checksums, sizes, paths and installation receipts must be reviewed after download approval and before install approval. No installer is allowed to substitute an unapproved package or restart automatically.

### R2B: first start and configuration, separately approved

1. **First-launch/VM-start approval required:** start Docker Desktop manually in a planned nongaming window. This may start WSL services and the Docker-owned Linux environment. That action is explicitly outside R1. Record only the newly created runtime resources for recovery; do not expose personal distribution names or inspect other users.
2. **Configuration approval required:** select WSL 2, keep unrelated distro integration off, Windows-login startup off, Kubernetes off, no remote daemon TCP exposure, no host networking, no GPU/AI/model/extension/offload features, and no financial-data mounts. 3. **Global WSL configuration approval required:** if selected, preserve any existing `.wslconfig` privately, review global effects and apply the proposed profile below. 4. **Metadata-check approval required:** verify WSL product version and distribution states and Docker client/server version, architecture, selected context and provider. Version/status commands may wake a runtime, so run only within the approved start window. Capture a minimal sanitized receipt; default `docker info` can contain unnecessary identifiers and must not be published wholesale.
5. **Qualification approval required:** compare available memory, disk growth, existing development behavior and shutdown behavior against baseline, with no containers or finance execution yet. Owner-controlled gaming/VPN/VM checks are separate; never launch them automatically. If the VM exceeds budget, steals development headroom or cannot shut down cleanly, stop and review.

R2 does not include `docker run hello-world`, image pulls, calculator builds, production signing keys, approved previews, journal reads, migrations or accepted saves. Any nonfinancial container smoke test still requires explicit approval. R3 would separately approve packaging, signing and sandbox/golden/recovery tests. ## 7. Stop, rollback and protection plan

- **No startup yet:** the lowest-risk rollback today is doing nothing; no runtime is installed or operationally qualified.
- **After an approved trial:** stop only AVA-owned worker/container IDs recorded by that trial, if any, then use Docker's tray **Quit Docker Desktop**. Inspect memory and owned distro state. Resource Saver is not proof that WSL memory has been released.
- **Residual owned environment:** obtain explicit approval before terminating a confirmed newly created Docker-owned distro/session. Never shut down all WSL, stop unrelated services, disable VBS or kill all node/Python processes. Stopping one owned runtime must not require changing application data.
- **Before uninstall/reset:** preserve and verify any later approved release archives, trust history and recovery instructions outside the runtime store. Do not use or overwrite the two existing journal backups for runtime recovery. Docker uninstall/reset can destroy its local images/volumes; this is a separately approved destructive step. [Docker uninstall](https://docs.docker.com/desktop/uninstall/), [backup/restore](https://docs.docker.com/desktop/settings-and-maintenance/backup-and-restore/).
- **Remove the selected runtime:** after explicit uninstall approval, use Windows Installed Apps or the exact verified installer's uninstall flow. Review the specific target first. No broad profile cleanup, recursive deletion, `system prune`, global distro unregister or registry cleanup is authorized. Residual files can be assessed separately.
- **Restore configuration:** restore only settings changed by this installation from its own receipt, with owner approval. Reverting newly enabled WSL features may require administrator rights and reboot and is allowed only after confirming nothing else now depends on them. Do not alter pre-existing hypervisor/VBS security merely because optional Hyper-V features were originally disabled.
- **WSL removal/distro unregister:** potentially destructive, requires separate explicit approval and a verified owned-resource inventory. It is not the default rollback and must never target another user's or existing practice/development environment.
- **Journal protection:** all runtime tests use disposable synthetic workspaces. Preserve existing source/migration hashes, environment configuration and processes; mount no journal or backups into the calculator. Regression tests on fresh databases can establish source behavior without accessing the normal journal. Any manual read of the normal journal, new backup/fingerprint inspection, stopping its writers or migration needs separate explicit authorization. Do not claim its contents were rechecked in R1.
- **Recovery rehearsal:** restore an approved calculator archive into a new isolated image store, verify signature and identity, replay golden data offline, then remove only that trial's verified resources. Missing artifacts or failed replay remain unavailable; there is no automatic fallback to current host code.
